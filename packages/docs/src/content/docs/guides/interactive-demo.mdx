## See the Diamond Dependency Glitch in Action

When two derived values depend on the same source (a **diamond dependency**), some reactive libraries emit inconsistent intermediate states — known as **glitches**. This demo lets you see the difference with your own eyes.

### How it works

Click and drag on each canvas to draw a trail. Each dot is placed by the library's reactive pipeline using the same **diamond dependency graph**:

```
mousePos (source: {x, y})
  ├── derivedX = map(pos => pos.x)
  ├── derivedY = map(pos => pos.y)
  └── combine([derivedX, derivedY])
        └── draw dot at {x, y} + check consistency
```

Each emitted position is compared to the latest mouse position:

- **Blue dot** — emitted `(x, y)` matches the actual mouse position (consistent)
- **Red dot** — one axis updated but the other didn't yet (glitch — the dot appears off the drag path)

### What to look for

| Library      | Glitches | Performance | Why                                                                                                                                |
| ------------ | -------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **SynState** | 0        | Fast        | Depth-based topological update — all branches resolve atomically before notifying subscribers                                      |
| **RxJS**     | Many     | Fast        | `combineLatest` fires on each input change, so `derivedX` updates before `derivedY` causing intermediate emissions with stale data |
| **Jotai**    | 0        | Slower      | Pull-based derivation ensures consistency, but re-computation overhead is higher per update                                        |

### Why this matters

In real applications, diamond dependencies appear everywhere — computed styles from shared state, derived UI values, form validations. Glitches cause:

- **Visual flicker** — UI renders an impossible intermediate state
- **Wasted renders** — extra emissions trigger unnecessary work
- **Logic bugs** — side effects fire with inconsistent data

SynState eliminates these problems at the library level, with no manual workarounds needed.

## Spring-Follower Chain: Performance Under Load

This demo shows how each library handles a **deep reactive chain**. A snake tail follows the mouse — each segment is a stage in a `scan` chain that smoothly follows the previous stage:

```
mousePos (head)
  → scan₁: lerp(self, head,    0.3) → tail[0]
    → scan₂: lerp(self, tail[0], 0.3) → tail[1]
      → scan₃: lerp(self, tail[1], 0.3) → tail[2]
        ...
```

Increase the chain depth with the slider. At higher values, the per-update cost grows — watch for stutter and rising μs/update.

<SpringDemo client:only="react" />

### What to look for

- At **low N** (10–50): all three libraries render smoothly
- At **high N** (200+): Jotai's `store.get()` / `store.set()` overhead per stage accumulates, causing visible stutter and higher μs/update
- SynState and RxJS handle deep chains efficiently thanks to push-based propagation
