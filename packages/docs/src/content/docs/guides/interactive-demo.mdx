## See the Diamond Dependency Glitch in Action

When two derived values depend on the same source (a **diamond dependency**), some reactive libraries emit inconsistent intermediate states — known as **glitches**. This demo lets you see the difference with your own eyes.

### How it works

Click and drag on each canvas to draw a trail. Each dot is placed by the library's reactive pipeline using the same **diamond dependency graph**:

```
mousePos (source: {x, y})
  ├── derivedX = map(pos => pos.x)
  ├── derivedY = map(pos => pos.y)
  └── combine([derivedX, derivedY])
        └── draw dot at {x, y} + check consistency
```

Each emitted position is compared to the latest mouse position:

- **Blue dot** — emitted `(x, y)` matches the actual mouse position (consistent)
- **Red dot** — one axis updated but the other didn't yet (glitch — the dot appears off the drag path)

<GlitchDemo client:only="react" />

### What to look for

| Library      | Glitches | Why                                                                                                                                |
| ------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **SynState** | 0        | Depth-based topological update — all branches resolve atomically before notifying subscribers                                      |
| **RxJS**     | Many     | `combineLatest` fires on each input change, so `derivedX` updates before `derivedY` causing intermediate emissions with stale data |
| **Jotai**    | 0        | Pull-based derivation ensures consistency — derived atoms always read the latest values                                            |

With only 2 derived values, all three libraries are fast enough that the performance difference is negligible. But the extra emissions from RxJS become a serious performance problem as the graph grows — see the [spring-follower demo below](#spring-follower-chain-performance-under-load).

### Why glitches matter

In real applications, diamond dependencies appear everywhere — computed styles from shared state, derived UI values, form validations. Glitches cause:

- **Visual flicker** — UI renders an impossible intermediate state
- **Wasted work** — each extra emission triggers unnecessary side effects. With N inputs to `combineLatest`, a single source update causes N+1 emissions — this scales to an **O(N²) performance cliff** as shown in the demo below
- **Logic bugs** — side effects fire with inconsistent data

SynState eliminates these problems at the library level, with no manual workarounds needed.

## Spring-Follower Chain: Performance Under Load

This demo shows how each library handles a **deep reactive chain**. A snake tail follows the mouse — each segment is a stage in a `scan` chain that smoothly follows the previous stage:

```
mousePos (head)
  → scan₁: lerp(self, head,    0.3) → tail[0]
    → scan₂: lerp(self, tail[0], 0.3) → tail[1]
      → scan₃: lerp(self, tail[1], 0.3) → tail[2]
        ...
```

To draw the full snake, all N stage outputs are collected with `combine` / `combineLatest`:

```
combine([source, scan₁, scan₂, ..., scanN]) → subscriber (draw snake)
```

Jotai doesn't have a `scan` operator, so the spring propagation is done imperatively: N writable atoms are updated via a write-derived "transaction atom" that batches all `store.set()` calls into a single flush. A derived atom reads all N stage atoms to produce the point array for drawing.

Increase the chain depth with the slider. At higher values, watch for stutter and rising μs/update.

<SpringDemo client:only="react" />

### What to look for

- At **low N** (10–50): all three libraries render smoothly
- At **high N**: RxJS starts stuttering first — check the **Total updates** counter to see why
- SynState and Jotai stay smoother at higher N, but Jotai shows higher μs/update due to per-operation overhead

### Why RxJS struggles here

Check the **Total updates** counter: RxJS shows roughly **N+1 times** more updates than SynState for the same mouse movement. `combineLatest` fires every time **any** of its N+1 inputs emits. On a single mouse move, the scan chain propagates sequentially:

1. `source` emits → `combineLatest` fires (only source updated, scans still hold old values)
2. `scan₁` emits → `combineLatest` fires again
3. `scan₂` emits → fires again
4. ... for all N stages

Each of these N+1 firings triggers a full canvas redraw of N+1 points → **O(N²)**.

This is the glitch problem from the first demo manifesting as a **performance cliff**: each intermediate emission triggers expensive side effects that compound with graph size.

### SynState vs Jotai

Both SynState and Jotai fire the subscriber **once** per mouse event, making them both **O(N)**. The difference is in the constant factor:

- **SynState**: push-based propagation through a declarative `scan` chain — the reactive graph does the work automatically
- **Jotai**: imperative propagation via a transaction atom (`store.set` N times within a write function) — Jotai batches these into one flush, but each `get()` / `set()` carries store overhead

#### Important caveat: different graph topologies

The reactive graph structures are **fundamentally different** between SynState/RxJS and Jotai:

- **SynState / RxJS**: a **depth-N chain** — `source → scan₁ → scan₂ → … → scanN → combine`. The framework's propagation engine walks N levels of dependencies per update.
- **Jotai**: a **flat graph** — N independent writable atoms + 1 derived atom that reads them all. The spring propagation (lerp loop) runs as plain JavaScript inside the transaction atom's write function, not as framework-managed dependency resolution. The reactive graph depth is just **1**.

This is not an unfair optimization — it is an inherent consequence of Jotai's design. Jotai derived atoms are pure functions of other atoms and **cannot reference their own previous value**, so a stateful operator like `scan` cannot be expressed as a chain of derived atoms. The imperative transaction atom pattern is the idiomatic Jotai approach.

As a result, this demo measures slightly different things for each library:

- **SynState / RxJS**: framework propagation cost through a deep dependency chain
- **Jotai**: store read/write throughput on a flat set of atoms

Jotai excels at derived state (pure functions of other atoms) while SynState handles streaming/stateful pipelines natively. Choosing between them depends on whether your use case is closer to **derived state** or **event-driven state machines**.

| Library      | Graph depth | Propagation                 | Subscriber calls per mouse event | Total work per event  |
| ------------ | ----------- | --------------------------- | -------------------------------- | --------------------- |
| **SynState** | N           | N stages (declarative push) | **1** (atomic combine)           | O(N)                  |
| **Jotai**    | 1           | N stages (imperative batch) | **1** (transaction atom)         | O(N), higher constant |
| **RxJS**     | N           | N stages (push)             | **N+1** (combineLatest glitch)   | O(N²)                 |
