## See the Diamond Dependency Glitch in Action

When two derived values depend on the same source (a **diamond dependency**), some reactive libraries emit inconsistent intermediate states — known as **glitches**. This demo lets you see the difference with your own eyes.

### How it works

Click and drag on each canvas to draw a trail. Each dot is placed by the library's reactive pipeline using the same **diamond dependency graph**:

```
mousePos (source: {x, y})
  ├── derivedX = map(pos => pos.x)
  ├── derivedY = map(pos => pos.y)
  └── combine([derivedX, derivedY])
        └── draw dot at {x, y} + check consistency
```

Each emitted position is compared to the latest mouse position:

- **Blue dot** — emitted `(x, y)` matches the actual mouse position (consistent)
- **Red dot** — one axis updated but the other didn't yet (glitch — the dot appears off the drag path)

<GlitchDemo client:only="react" />

### What to look for

| Library      | Glitches | Why                                                                                                                                |
| ------------ | -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **SynState** | 0        | Depth-based topological update — all branches resolve atomically before notifying subscribers                                      |
| **RxJS**     | Many     | `combineLatest` fires on each input change, so `derivedX` updates before `derivedY` causing intermediate emissions with stale data |
| **Jotai**    | 0        | Pull-based derivation ensures consistency — derived atoms always read the latest values                                            |

With only 2 derived values, all three libraries are fast enough that the performance difference is negligible. But the extra emissions from RxJS become a serious performance problem as the graph grows — see the [deep dependency chain demo below](#deep-dependency-chain-propagation-under-load).

### Why glitches matter

In real applications, diamond dependencies appear everywhere — computed styles from shared state, derived UI values, form validations. Glitches cause:

- **Visual flicker** — UI renders an impossible intermediate state
- **Wasted work** — each extra emission triggers unnecessary side effects. With N inputs to `combineLatest`, a single source update causes N+1 emissions — this scales to an **O(N²) performance cliff** as shown in the demo below
- **Logic bugs** — side effects fire with inconsistent data

SynState eliminates these problems at the library level, with no manual workarounds needed.

## Deep Dependency Chain: Propagation Under Load

**Purpose:** This demo measures the **serial dependency chain propagation performance** of each reactive framework. All three libraries build an identical reactive graph topology: a **depth-N chain** of stateful nodes where each depends on the previous, with a final combine/derive that reads all N+1 outputs.

A snake tail follows the mouse — each segment is a stage in the chain that smoothly follows the previous stage via linear interpolation (lerp):

```
mousePos (head)
  → scan₁: lerp(self, head,    0.3) → tail[0]
    → scan₂: lerp(self, tail[0], 0.3) → tail[1]
      → scan₃: lerp(self, tail[1], 0.3) → tail[2]
        ...
```

To draw the full snake, all N stage outputs are collected:

```
combine([source, stage₁, stage₂, ..., stageN]) → subscriber (draw snake)
```

All three libraries use the same **depth-N chain** graph topology. The key difference is how `scan` (stateful derivation) is expressed:

- **SynState**: `source.pipe(scan(lerp))` — native `scan` operator, depth-N chain
- **RxJS**: `source$.pipe(scan(lerp))` — native `scan` operator, depth-N chain
- **Jotai**: `selectAtom(prevStage, (target, prevSelf) => lerp(prevSelf, target))` — `selectAtom` provides access to the atom's own previous output, acting as a scan equivalent. Depth-N chain of derived atoms

Increase the chain depth with the slider. At higher values, watch for stutter and rising μs/update.

<SpringDemo client:only="react" />

### What to look for

- At **low N** (10–50): all three libraries render smoothly
- At **high N**: RxJS starts stuttering first — check the **Total updates** counter to see why
- SynState and Jotai stay smoother at higher N, but Jotai shows higher μs/update due to per-atom store overhead in its pull-based engine

### Why RxJS struggles here

Check the **Total updates** counter: RxJS shows roughly **N+1 times** more updates than SynState for the same mouse movement. `combineLatest` fires every time **any** of its N+1 inputs emits. On a single mouse move, the scan chain propagates sequentially:

1. `source` emits → `combineLatest` fires (only source updated, scans still hold old values)
2. `scan₁` emits → `combineLatest` fires again
3. `scan₂` emits → fires again
4. ... for all N stages

Each of these N+1 firings triggers a full canvas redraw of N+1 points → **O(N²)**.

This is the glitch problem from the first demo manifesting as a **performance cliff**: each intermediate emission triggers expensive side effects that compound with graph size.

### SynState vs Jotai

Both SynState and Jotai fire the subscriber **once** per mouse event, making them both **O(N)**. The difference is in the constant factor per update:

- **SynState**: push-based — the framework propagates through the depth-N `scan` chain via direct function calls and fires `combine` once after all stages are resolved. The propagation order is resolved once at subscribe time.
- **Jotai**: pull-based — each `store.set()` triggers (1) a DFS invalidation pass marking all N dependents as stale, (2) a DFS topological sort to determine recomputation order, (3) recomputation of each `selectAtom` via `get()` with epoch-based staleness checks and dynamic dependency tracking. **The topological sort is performed on every update**, not once at setup time. See the [benchmark analysis](/synstate/guides/benchmark/#analysis-why-jotai-is-29-slower) for details.

| Library      | Graph depth | Propagation   | Subscriber calls per mouse event | Total work per event  |
| ------------ | ----------- | ------------- | -------------------------------- | --------------------- |
| **SynState** | N           | push (atomic) | **1** (atomic combine)           | O(N)                  |
| **Jotai**    | N           | pull (lazy)   | **1** (derived read)             | O(N), higher constant |
| **RxJS**     | N           | push (eager)  | **N+1** (combineLatest glitch)   | O(N²)                 |

## Throughput: Per-Update Overhead Under Load

The deep dependency chain demo above shows that SynState and Jotai both fire the subscriber **once** per source update (unlike RxJS). But they are **not equally fast** — SynState's push-based engine has significantly less per-update overhead than Jotai's pull-based engine. This demo makes that constant-factor difference visible.

### How it works

A ball automatically orbits in a circle. Each canvas runs the **same depth-M reactive chain** as the spring demo above. The difference: instead of 1 source update per mouse event, **K source updates are pushed through the chain every animation frame** in a tight synchronous loop.

```
each animation frame:
  for k in 0..K-1:
    update source position (micro-step along orbit)
    → propagate through depth-M scan chain
    → subscriber records latest points
  draw snake once
```

This amplifies the per-update overhead by a factor of K. When `K × (per-update cost)` exceeds 16ms, the animation drops frames and stutters.

<ThroughputDemo client:only="react" />

### What to look for

- At **low K** (1–100): both libraries animate smoothly
- **Increase K** toward 500–1000: Jotai's **ms/frame** climbs past 16ms and the animation visibly stutters, while SynState remains smooth
- The **ms/frame** indicator turns red when it exceeds the 16ms budget (60fps threshold)

### Why Jotai stutters

Each of the K source updates triggers Jotai's full update pipeline:

1. `store.set()` → DFS invalidation of M dependents → O(M)
2. DFS topological sort to determine recomputation order → O(M)
3. Recompute each `selectAtom` with epoch checks and dynamic dependency tracking → O(M)

**Total per frame: K × O(M) with high constant factor** (Map/WeakSet allocations, epoch comparisons, two DFS traversals per tick).

SynState's push-based engine propagates through the same chain via **direct function calls** with the propagation order resolved once at subscribe time — no per-update graph traversal, no dynamic dependency tracking, no epoch bookkeeping.

| Library      | Per-update work                                | K=500, M=100 |
| ------------ | ---------------------------------------------- | ------------ |
| **SynState** | 100 direct function calls                      | ~2–5ms       |
| **Jotai**    | 2× DFS(100) + 100 epoch-checked recomputations | ~50–100ms    |
